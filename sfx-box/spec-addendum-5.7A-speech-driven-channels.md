# §5.7A — Speech-driven channels

*Draft addendum for `sfx-box-spec.md`. Written 2026-09-09 against spec v0.5.*

---

## Why this section exists

§5.7 introduced speech-sync as part of the **motion** subsystem, because both instances
that existed were motion:

| Prop | Track | Actuator |
|---|---|---|
| Ghost Host / Nosferatu | word timestamps | DC gearmotor via H-bridge — jaw |
| Zoltar | word timestamps | servo — jaw |

The Tiki fire bar is the third instance, and it is **not motion at all**: word-level speech
drives a field of addressable pixels so that a simulated fire appears to speak. Nothing
moves. There is no rest angle, no coast, no stall current, no watchdog against a stuck
motor.

That is the signal. When a third instance of a pattern lands outside the subsystem the
pattern was filed under, the abstraction is one level too low. **Speech-sync is not a
motion capability that happens to have two motion clients. It is a rendering capability
whose first two clients happened to be motion.**

This section lifts it, and — per §5.8's rule — adds vocabulary to the existing `play`
binding rather than creating a parallel one.

---

## The two axes

§5.7 conflated two independent things. Separating them is the whole of this change.

**Axis 1 — the track.** What the speech data *is*. A sidecar on the audio asset (§5.8).

| Kind | Shape | Generated by | Character |
|---|---|---|---|
| `word_timestamps` | `words[]` of `{text, start, end, type}` | STT forced alignment (ElevenLabs `scribe_v1` → OpenAI → local) | **Discrete.** Events with edges. |
| `speech_envelope` | uint8 pairs at 50 Hz — `level`, `onset` | local DSP at upload (ffmpeg + numpy) | **Continuous.** A curve. |

**Axis 2 — the renderer.** What the track drives.

| Kind | Output | Shaping parameters it owns |
|---|---|---|
| `MOTOR` | H-bridge drive/coast | `min_open`, `close_delay`, `max_open`, `stop_mode` |
| `SERVO` | angle | `open_angle`, `closed_angle`, slew limit |
| `PIXEL` | addressable light field | `speech_gain`, `attack`, `release`, `spread`, palette |

The cross product is legitimate, and this is the payoff:

|  | `word_timestamps` | `speech_envelope` |
|---|---|---|
| `MOTOR` | Ghost Host today | proportional drive time per syllable |
| `SERVO` | Zoltar as designed | **proportional jaw opening — better than binary, free** |
| `PIXEL` | flare per word — a lightning-strike character | **the Tiki fire** |

Note what falls out. Zoltar's jaw currently snaps between two angles because a timestamp
track has no middle. Give the same servo an envelope and it opens *by how loud the syllable
is*. That is not a new feature anyone asked for; it is a consequence of no longer assuming
the track kind and the actuator kind are one choice.

**No renderer is built into a track kind, and no track kind is built into a renderer.** A
channel declares which renderer it is; a `play` binding names which track to use; the
platform refuses combinations only where the mapping is genuinely undefined.

---

## What does not change

**The clock.** §5.7's most important decision stands untouched:

> The platform binds a speech-sync track to a playback handle and derives all timing from
> that handle's actual start, so sync is defined rather than incidental.

Every renderer inherits this. There is still one clock, still owned by the playback handle,
still never a second `time.time()` in a second thread. The two-clock bug §5.7 diagnosed in
Ghost Host is foreclosed for pixels by construction, not by discipline.

**Authoring-time generation.** Both track kinds are produced when the asset is uploaded,
never at trigger time. The envelope is cheaper than alignment — it is local DSP, no
provider, no network — but it is generated in the same place for the same reason.

**A missing track is not an error.** No sidecar → the audio plays, the renderer sits at
rest, the UI offers one-click generation. Unchanged from §5.7, and it now covers a fire
that simply keeps burning its idle pattern.

**Sidecar lifecycle.** §5.8 already predicted this exact addition — *"a loudness envelope
for smarter ducking… cue markers for lighting hits — all arrive as new kinds, reusing
generation, storage, listing, and lifecycle."* `speech_envelope` is that kind. It needs no
new upload path, no new delete path, no new list.

---

## What is genuinely new: remote renderers

Ghost Host and Zoltar render on the same Pi that plays the audio. A GPIO write is
microseconds from the clock that scheduled it.

The Tiki fire renders on a **battery-powered ESP32-C3 at the far end of a radio link**. That
is the first renderer the box cannot drive directly, and it introduces one problem the local
case never had: the renderer holds its own copy of the track and steps it on its own crystal.

> The transport is **ESP-NOW**, reached through a USB-attached bridge — see Addendum 2 at the
> end of this document. This section was drafted while the transport was still WiFi/UDP; the
> reasoning below is unchanged by the switch, and Addendum 2 says why.

The resolution keeps §5.7's principle rather than abandoning it:

- **The track lives on the renderer**, pushed at provisioning time, not streamed at show
  time. 2 bytes per frame at 50 Hz is 100 B/s — a 15 s greeting is 1.5 kB. There are no
  packets during the performance, so packet loss during a greeting is not a failure mode
  that exists.
- **The cue carries the clock.** `play` sends `{clip_id, position_ms, lead_ms}` at actual
  playback start, read from the playback handle — not from when the engine decided to play.
- **The clock is re-asserted, not assumed.** mpv already exposes `time-pos`; the box sends
  a position update every ~2 s. The renderer eases toward it rather than jumping. This is
  the difference between a remote renderer and a remote *timer*: a free-running envelope
  would be exactly the guess this project keeps removing.
- **Completion is an event, not a duration.** The existing `end-file`/`eof` callback — the
  one the eyes already use — releases the renderer to idle. A greeting aborted mid-sentence
  returns the fire to its resting burn, because it was told, not because it timed out.
- **`lead_ms` is tunable per channel.** The Pi's own audio-start jitter is tens of
  milliseconds and depends on the ALSA path. Light arriving slightly early reads as natural;
  late reads as broken. This is a measured trim, not a constant, and it must not require a
  reflash.

**Rest state applies here too.** §5.7 demands a guaranteed rest on every exit path. For a
`PIXEL` renderer, rest is the idle pattern — not black. The §5.6 lesson about parking an
output at its safe state generalises: for a fire, *dark is not safe, it is broken*, because
a fire that goes out reads as a fault while a fire that keeps burning reads as the prop
working. Decide what "safe" means for the load, then make that the un-owned state.

## Where this lands in the code

| Concern | Home | Change |
|---|---|---|
| Envelope generation | `media.py` | New sidecar kind beside `normalized_pcm`. ffmpeg + numpy, ~10 lines. |
| Track selection | the `play` binding | `sync: {track: envelope, channel: fire}` — vocabulary, not a new verb |
| Channel registry | `hardware.py` / `pinmap.py` | `PIXEL` joins as a kind. A *remote* pixel channel consumes no GPIO — the registry gains an address instead of a pin |
| Cue transport | new, small | ESP-NOW frames to a MAC, via the serial bridge on a USB-attached XIAO (Addendum 2). `peers.py` is the wrong home: peers are whole-performance triggers with a 3 s timeout and four outcomes. This is a clock feed |
| Renderer | on the ESP32 | The box sends a track and a clock. It does not send colours |

That last row is a boundary worth stating: **the box owns the speech, the renderer owns the
aesthetics.** The fire simulation, its palette, its flare behaviour and its idle burn live on
the ESP32 and are none of the box's business. The box says "the speech is here, at this
level, at this instant." A jaw renderer gets the same sentence and opens a mouth with it.

---

## Failure modes this forecloses

- **Two clocks.** The bug §5.7 named in Ghost Host, now impossible for a third actuator kind.
- **A parallel lighting subsystem.** Without this section, pixels arrive next season as their
  own action, their own sidecar, their own scheduler — precisely what §5.8 was written to stop.
- **Timestamp-shaped thinking about continuous actuators.** A fire driven by word boundaries
  strobes; it does not burn. Forcing the fire through `word_timestamps` would have produced a
  worse effect and then blamed the effect.
- **Streaming the envelope.** Tempting, and wrong: it puts the network on the show's critical
  path for the entire duration of the greeting rather than for one packet.

---

## What it means for each prop

- **Ghost Host / Nosferatu** — unchanged behaviour. Reclassified as `word_timestamps` × `MOTOR`.
  Gains the option of an envelope later.
- **Zoltar** — unchanged as specified, but `word_timestamps` × `SERVO` becomes
  `speech_envelope` × `SERVO` with one config change, and the jaw stops being binary.
- **Tiki** — `speech_envelope` × `PIXEL`, remote. The first remote renderer.

---

## Open questions

1. **Does the envelope belong to the asset or the performance?** Today, the asset. When the
   oracle module generates speech at runtime, the envelope must be produced as part of the
   TTS step — the same treatment §5.7 already specifies for alignment tracks.
2. **Should `PIXEL` cover local strips too?** A pixel channel driven from the Pi's own GPIO is
   the same renderer without the clock-correction problem. Probably yes, and it should not be
   a second kind.
3. **Multiple renderers on one `play`.** A jaw *and* a fire on the same greeting is two
   bindings on one handle. The model allows it; nothing has tested it.
4. **Envelope generation without ffmpeg.** `media.py` degrades to no sidecars off-Pi. The
   envelope has the same dependency and should degrade the same way, not fail.

## Addendum, 2026-09-09: ambience, and where the track lives

Two refinements from Steve that change the shape of the `PIXEL` renderer.

### Ambience is the light equivalent of the `ambient` voice

The renderer does not run "a fire". It runs a **named ambience**, selected by the box:

    fire     deep reds and orange, breathing, occasional flare
    water    blues and cyans, slower, caustic ripple
    ember    the same palette as fire at a fraction of the energy
    storm    near-dark with flash density

This is exactly the `ambient` voice's contract applied to light. The background audio track
is named, loops, runs without supervision, and ducks under the greeting. The ambience is
named, loops, runs without supervision, and is **excited** by the greeting. One concept, two
media. `player.py`'s naming note applies unchanged: the code says ambience, the page says
"Background".

The consequence worth stating: **the box selects an ambience by name and never describes
it.** It does not send colours, palettes, flicker rates or flare timing. `fire` and `water`
differ entirely inside the renderer. Swapping the tiki's fire for water is one string in a
show script, and nothing in the box knows what changed.

### Excitation: the one number the box sends

Speech reaches the renderer as a scalar, not as a lighting instruction:

    excitation ∈ [0,1]    how hard the speech is driving, right now
    onset      ∈ [0,1]    transient strength, for hits on plosives

**Every ambience interprets those two numbers in its own terms:**

| Ambience | rising `excitation` | `onset` |
|---|---|---|
| `fire` | hotter, brighter, wider — hue climbs toward yellow | a crackle flare |
| `water` | faster ripple, brighter caustics, toward white-cyan | a splash |
| `storm` | more frequent flashes | a strike |

This is what makes the capability generic rather than fire-specific. The same two numbers
drive a jaw's opening angle on a `SERVO` renderer. The box's sentence is always *"the speech
is at this level, at this instant"* — never *"be orange now."*

An ambience declares its own excitation response the way §5.7's channels declare their
shaping parameters. Adding `water` adds no vocabulary to the box.

### The track is resident before playback starts — it is not streamed

Both routes were considered. The resident track wins, and not narrowly.

**Streaming 50 Hz of modulation packets** puts the network on the show's critical path for
the entire greeting. A 15 s line is ~750 packets, each one carrying a frame that is visible
if it goes missing. Home WiFi jitter runs 10–100 ms with occasional half-second stalls —
which is precisely the syllable timescale, so the failure is not subtle. It is also the one
design that makes an access-point hiccup mid-greeting look like the prop is broken.

ESP-NOW's own latency is 1–3 ms, which removes the jitter argument but not the conclusion:
streaming still puts a radio on the show's critical path for the whole greeting, for no gain
over a 1.5 kB push beforehand. Bandwidth to spare is a reason to be careful, not a licence.

**A resident track** is 2 bytes per frame at 50 Hz — 100 B/s, so a 15 s greeting is 1.5 kB,
one burst. During the performance the network carries the cue, a position update every
couple of seconds, and nothing else. **Packet loss during a greeting stops being a failure
mode that exists.**

The obvious objection is generated speech: the oracle module has no track at provisioning
time because the audio does not exist yet. That does not break the model — the envelope is
local DSP over a file that was just written, milliseconds with numpy, and 1.5 kB pushed over
the link is a few more. **The rule is "resident before playback starts", not "resident since
yesterday."** Canned clips are pushed at provisioning; generated ones are pushed between TTS
returning and `play` being called.

### The timing exchange

Three messages, and deliberately no clock-synchronisation protocol:

1. **`ambience <name>`** — sent whenever the show changes it, and at connect. Idempotent. The
   renderer crossfades rather than cutting.
2. **`cue <clip> <t_ms> <lead_ms>`** — sent at *actual* playback start, with the position read
   from the playback handle. Not when the engine decided to play.
3. **`pos <t_ms>`** — every ~2 s while playing. The renderer **eases toward** it rather than
   jumping; a visible correction is worse than the drift it fixes.

Completion is the existing `end-file`/`eof` event, the one the eyes already use. The
renderer returns to its ambience because it was told, not because a timer expired — so a
greeting aborted mid-sentence settles correctly.

**`lead_ms` is a per-channel measured trim.** The Pi's audio-start jitter depends on the
ALSA path and is tens of milliseconds; light slightly early reads as natural, late reads as
broken. Tunable without a reflash.

**No NTP, no PTP, no RTT handshake — yet.** Position updates every 2 s plus a trimmed
`lead_ms` hold a 15 s greeting well inside perception, and a C3's crystal drifts under a
millisecond over that span. If a much longer piece ever shows drift between corrections,
measure RTT at cue time and subtract half of it. That is an escalation, not a v1 requirement,
and building it first would be solving a problem nobody has measured.

### Which track kind the fire wants

Steve's sketch said "companion timestamp file". For a **jaw** that is right — word boundaries
are what a mouth does. For a **fire** it is the wrong sidecar: word-boundary events make a
fire strobe rather than burn, because a fire has no open and closed state to toggle between.

The fire wants `speech_envelope`. But both sidecars can live on one asset, and the best
result uses both:

- **envelope** → syllable-level motion, the continuous drive
- **word timestamps** → phrase structure: let the fire visibly settle between phrases so the
  next surge lands harder, and allow bigger flares on emphasised words

That is the two-axis model paying off in a single prop. The binding names which track a
renderer consumes; nothing stops a renderer consuming two.

## Addendum 2, 2026-09-09: the tiki stays infrastructure-free

**Constraint added by Steve, and it governs.** The Tiki today runs its eyes over 433 MHz
relays and needs no WiFi at all. Putting the light bar on WiFi would make the *whole prop*
depend on an access point it currently doesn't need — not just the new channel. That is a
new failure mode for a prop that already works, introduced for one feature.

Weigh it that way and it isn't close. A prop that degrades when the router reboots is worse
than a prop with one more radio in it.

### The distinction that resolves it

**ESP-NOW is not WiFi networking.** It uses the 2.4 GHz WiFi radio and nothing else from the
stack: no access point, no SSID, no association, no DHCP, no router. Two ESP32s address each
other by MAC. The link comes up when both ends have power and stays up with every router in
the building switched off.

So "no WiFi dependence" and "use the WiFi radio" are compatible. The dependency being removed
is on *infrastructure*, not on a frequency band.

### Chosen transport: ESP-NOW, bridge on the Pi's USB

| | |
|---|---|
| Light bar | XIAO ESP32C3 — radio already on board, no added hardware |
| SFX box | second XIAO ESP32C3 on USB, running a serial ⇄ ESP-NOW bridge |
| Extra parts to buy | **none** — Steve owns a pair of C3s |
| Payload | 250 bytes, hundreds of packets/s available |
| Latency | 1–3 ms |
| Security | AES-128 per peer |
| Delivery | per-packet callback — the box learns whether the bar heard it |

The Pi 4 cannot transmit ESP-NOW on its own radio: the protocol rides 802.11 vendor-specific
action frames and needs monitor mode with packet injection, which the onboard CYW43455 does
not do under Raspberry Pi OS. Hence the bridge.

**The resident-track model is unchanged and matters more here, not less.** ESP-NOW has
bandwidth to spare and could stream 50 Hz comfortably — which is exactly the argument that
tempts you into putting a radio on the show's critical path. Don't. The track is pushed
before playback starts; the performance carries a cue, a position update every ~2 s, and
nothing else.

**One capability this gains over both WiFi and 433: the bar can answer.** Battery level, an
"I'm alive" heartbeat, and confirmation that a cue landed can all come back on the same link.
`health.py` has somewhere to put that; a one-way 433 channel never could.

### Options considered and not taken

**nRF24L01+ on the Pi's SPI.** Genuinely attractive: the Pi drives the radio directly, so
there is no USB co-processor, and it registers in `pinmap.py` / `hardware.py` as a module
with pins like every other — architecturally the cleanest fit to the existing registry.
Rejected for now on cost of change: ~5 GPIO off a harness plate that is already built and
allocated, a new driver in `rf.py`'s shape, and two modules to buy. **Revisit if the USB
bridge proves annoying** — the protocol above is transport-agnostic and would port.

**RFM69 / CC1101 at 433 MHz.** Sub-GHz, better penetration, SPI both ends. Rejected because
it puts data traffic in the same band as the EV1527 relay commands driving the eyes. The
relay receiver would see the data as noise, but noise during a keypress is a missed keypress,
and §5.9 already documents how badly a lost packet behaves on a toggle-mode relay.

**Extending the existing EV1527 link.** Four discrete channels can select an ambience. They
cannot carry a clip id, a position, or a correction. Using them for speech would mean the bar
free-runs a generic "talking" animation with no relationship to the actual words — which
abandons the entire point of the feature while appearing to deliver it.

**Wiring it.** Not evaluated: the eyes being on 433 relays implies the box is not physically
at the tiki. If that is wrong and the box is in the tiki base, a wire beats every radio here
and this whole section is moot — worth confirming before building.

### Record of the reversal

ESP-NOW was recommended first, then changed to WiFi/UDP on reading that `peers.py` already
addresses props over the network, then changed back here. The middle position was not wrong
on its own terms — it was wrong because it optimised for fitting the box's existing network
model without knowing the tiki was deliberately network-free. **The constraint is the new
information, and it outranks the architectural tidiness that displaced it.**

## Addendum 3, 2026-09-09: the prop is a venue, not the product

**Context that closes the loop.** The SFX box is a general-purpose effects controller — a
multi-functional device, not a tiki controller. The Tiki is a **borrowed** prop: the wireless
gear is removed at the end of the season and the eyes revert to a plain power supply. The
light bar is *placed* in the mouth, not installed.

This is the strongest argument yet for everything above, and it should be stated in the spec
rather than left implicit:

> **The box and its channels outlive the prop.** A prop is a venue a capability visits for a
> season. Nothing in the platform should encode which prop it is currently sitting in.

Three things follow.

**The renderer is prop-agnostic hardware.** It is not "the tiki fire bar." It is a portable
speech-driven light bar that this season lives in a tiki, and next season lives in a cauldron,
a fireplace, a lantern or a skull. Naming it after the tiki would be the same category error
as filing speech-sync under motion.

**Ambience-by-name earns its keep here, not in the tiki.** A fixed installation could have
hard-coded fire and lost nothing. A device that moves between props every season needs
`fire`, `water`, `storm` selectable by a string — because the *prop changes and the hardware
does not*. §5.8's rule about naming being the interface is doing real work.

**Everything the effect depends on travels with the device.** Including the surface it lights:
the diffusing backdrop is part of the bar's assembly, not something applied to the venue. A
capability that requires modifying its host cannot move, and this one has to.

### What this implies for commissioning

A portable renderer is re-paired more often than a fixed one. ESP-NOW peers are addressed by
MAC, so pairing has to be an operator action rather than a config-file edit — the same shape
as §5.9's RF pairing and the RX480E's learn button, and for the same reason. Assume the bar
will be paired to a different box, or the box to a different bar, at least once a season.

### And a caution the borrowed prop adds

**Rest state is now also a returnability requirement.** A renderer left holding an unknown
state in someone else's prop is worse than one that is merely wrong — the owner gets the
thing back with a light in it doing something. §5.7's guaranteed-rest rule should extend to
*power removal*: the device must be safe and inert when the battery is pulled, with no
retained state that surprises anyone later.
